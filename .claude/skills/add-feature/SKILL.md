# 機能追加: $ARGUMENTS

以下の手順で機能を追加する。

**重要: 各ステップの完了時にユーザーの承認を得てからコミットする。承認なしにコミットや次のステップへの移行を行ってはならない。**

## 1. Domain 層を設計する

エンティティ（Valibot スキーマ + brand）、Repository インターフェース、ドメインエラーを定義する。

→ ユーザーに設計内容を提示し、承認を得てからコミットする。

## 2. 統合テストを書く（Red）

- `src/server/api/routers/__tests__/` に統合テストを作成する
- 正常系を最低1ケース、異常系はドメインエラーを返すパスをすべてカバーする
- テストを実行し、失敗することを確認する

```bash
pnpm --filter web test
```

→ 承認を得てからコミットする。

## 3. バックエンドを実装する（Green）

ステップ1で定義した Domain 層をベースに、残りの層を以下の順で実装する:

1. **UseCase 層**: Domain の Repository インターフェースに依存し、クラスとして定義する。UseCase はユーザーの意図ごとに用意する
2. **Infrastructure 層**: Domain の Repository インターフェースを実装し、DI コンテナに登録する
3. **API 層**: tRPC ルーターで UseCase を呼び出す

テストを実行し、すべて通ることを確認する。

```bash
pnpm --filter web test
```

→ 承認を得てからコミットする。

## 4. リファクタする

テストが通る状態を維持しつつ、コードを整理する。

→ ステップ 2〜4 の実装内容をまとめてユーザーに提示し、承認を得てからコミットする。

## 5. UX/UI を設計する

以下の順で設計し、ユーザーに提示する。装飾は最低限にとどめ、UX を重視する。見た目は後からリッチにできる余地を残す。

1. **ユーザーフローを定義する**: 対象機能の受け入れ条件から、ユーザーが目的を達成するまでの操作手順を洗い出す。画面遷移・分岐・エラー時の動線を明確にする
2. **ワイヤーフレームを作成する**: ユーザーフローに基づき、`dev/<feature>/page.tsx` にモックページを作成する。レイアウトと情報配置に集中し、各画面の状態（ローディング・空・エラー）も考慮する
3. **ユーザビリティを検証する**: ニールセンの10ヒューリスティクスに照らし、明らかな問題がないか確認する

必要な shadcn/ui コンポーネントは承認なしでインストールしてよい。

→ ユーザーフローとワイヤーフレームを提示し、承認を得てからコミットする。

## 6. フロントエンドを実装する

以下の順で実装する:

1. **page.tsx**（Server Component）: `metadata` の設定と `_components/` 内のメインコンポーネントの呼び出しのみ
2. **_components/ のメインコンポーネント**（Client Component）: データ取得・UI・インタラクションを担当する
3. **UI コンポーネント**: shadcn/ui をベースにする。新しい shadcn コンポーネントが必要な場合は、`packages/ui/` へのインストールのみを単独のコミットとして作成してから、実装に進む

- 必要に応じて開発用シード（`src/server/infrastructure/db/seed.ts`）を追加し、画面確認に使う

→ 承認を得てからコミットする。

## 7. E2E テストを書く

- `e2e/` に機能単位で E2E テストを作成する
- 必要に応じて E2E 用シード（`e2e/seed.ts`）を追加する
- テストを実行し、すべて通ることを確認する

```bash
pnpm --filter web test:e2e
```

→ 承認を得てからコミットする。
