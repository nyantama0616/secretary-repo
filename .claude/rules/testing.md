## 方針

統合テスト + E2E の2層構成を基本戦略とする。この組み合わせはプロダクトの種類を問わず汎用的に機能する土台であり、プロダクトの性質に応じてテスト種別（ユニットテスト、ビジュアルリグレッション等）を追加する。

## テストの種類

このプロジェクトでは以下の2種類のテストを書く。

| 種類 | ツール | 対象 | 配置 |
|---|---|---|---|
| 統合テスト | Vitest | tRPC ルーター（バックエンド全層） | `src/server/api/routers/__tests__/{domain}.test.ts` |
| E2E テスト | Playwright | ユーザー操作フロー（画面） | `e2e/{feature}.test.ts` |

書かないテスト:
- コンポーネントテスト（Testing Library 等）は書かない。画面の検証は E2E で行う
- Domain 層・UseCase 層のユニットテストは、ロジックが複雑化して統合テストでのカバーが困難になった時点で導入を検討する

## いつどのテストを書くか

### 統合テスト（必須）

tRPC ルーターの追加・変更時に書く。

検証すること:
- 各プロシージャの正常系を最低1ケース（返り値の構造と値）
- 異常系はドメインエラーを返すパスをすべてカバーする（NOT_FOUND、CONFLICT など）
- DB に正しくデータが永続化されること（作成・更新・削除の結果）

検証しないこと:
- UI の表示やユーザー操作（E2E の責務である）
- 入力バリデーションのエッジケース（Valibot スキーマが担保する。スキーマ定義が正しければ個別テスト不要）
- Infrastructure 層の内部実装（SQL の発行内容や DB ドライバの挙動）

### E2E テスト（機能単位で書く）

機能（ユーザー管理、注文管理など）ごとに1ファイルを作成し、その機能の主要な操作フローをカバーする。

以下の場合に追加・更新する:
- 新しい機能を追加したとき
- 既存機能のユーザー操作フローを変更したとき

検証すること:
- 画面遷移が正しく動くこと（リンク、フォーム送信後のリダイレクトなど）
- ユーザーに必要な情報が表示されること（一覧、詳細など）
- フォーム操作が正しく完了し、結果が画面に反映されること
- エラー時にユーザーにフィードバックが表示されること（代表的なケースを1つ）

検証しないこと:
- ビジネスロジックの網羅的なエッジケース（統合テストの責務である）
- 異常系の全パターン（統合テストで網羅済み。E2E では「エラーが表示される」ことの確認に留める）
- API レスポンスの構造や値の詳細（統合テストの責務である）
- スタイリングやレイアウトの詳細

## 統合テストの書き方

`createCaller` で tRPC ルーターを直接呼び出す。HTTP サーバーは起動しない。

### テストデータ

- テスト内で `db.insert()` を使って直接投入する
- 全テーブルの TRUNCATE は `src/test/setup.ts` の `beforeEach` で自動実行されるため、テスト側でのクリーンアップは不要である
- テストデータはファイル先頭に定数として定義する

### 構造

- `describe` はプロシージャ名（`user.list`、`user.create` など）で分ける
- `it` のテスト名は日本語で、「`{期待する振る舞い}`」の形式で書く。条件がある場合は「`{条件}の場合、{期待する振る舞い}`」とする

## E2E テストの書き方

### テストデータ

- `e2e/seed.ts` でシードデータを投入する。`globalSetup` で実行される
- テストはシードデータが存在する前提で書く
- シードデータの変更が必要な場合は `e2e/seed.ts` を更新する

### 構造

- `test.describe` は機能単位（「ユーザー管理」など）で分ける
- `test` のテスト名は日本語で、「`{操作}すると、{期待結果}`」の形式で書く。条件がある場合は「`{条件}で{操作}すると、{期待結果}`」とする
- ページ操作には `getByRole`、`getByLabel`、`getByText` などのアクセシブルなセレクタを使う。要素を特定できない場合は `data-testid` を追加するのではなく、UI のアクセシビリティを改善する
