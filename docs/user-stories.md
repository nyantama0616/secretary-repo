# ユーザーストーリー

## フォーマット

ユーザーストーリーは以下の形式で記述する。

```
[ユーザー]として、[達成したいこと]をしたい。なぜなら[理由・動機]だからだ。
```

これは "As a [user], I want [goal], so that [reason]." という国際的に広く使われる形式に基づく。

### 各要素の説明

| 要素 | 説明 | 例 |
|---|---|---|
| ユーザー | 誰がその機能を使うのか | 利用者、管理者 |
| 達成したいこと | 何をしたいのか（機能・行動） | 今日のタスク一覧を見たい |
| 理由・動機 | なぜそれが必要なのか（価値） | 何をすべきか迷わないため |

### 受け入れ条件（Acceptance Criteria）

各ストーリーには「何をもって完了とするか」を受け入れ条件として記述する。

```
- [ ] 条件1
- [ ] 条件2
```

### 優先度

| ラベル | 意味 |
|---|---|
| Must | MVPに必須。これがないと使い始められない |
| Should | 早期に欲しいが、初回リリースには必須ではない |
| Could | あると嬉しいが、なくても成立する |
| Won't | 今は作らない。将来の検討事項 |

これは MoSCoW法 と呼ばれる優先度分類である。

## ストーリー一覧

### US-001: AIによる翌日のタスク提案

**優先度:** Must

利用者として、翌日やるべきことをAIに提案してもらいたい。なぜならタスクを自分で一から考える手間を減らし、翌日の行動に迷いなく取りかかれるようにしたいからだ。

**詳細:**
- 利用者が「明日のタスクを提案して」などと指示すると、AIが翌日のタスクを提案する
- AIは以下の情報をもとに提案を組み立てる
  - 自前DBに登録されている既存のタスク（未完了タスクの優先順位づけ）
  - Googleカレンダーの予定（予定に対して不足しているタスクの追加提案）
- 提案には取り組む順番が含まれ、最初に着手すべきタスクが明確である
- 提案に対して、利用者は以下の操作ができる
  - 承認する（提案内容をそのまま翌日のタスクとして確定する）
  - AIにフィードバックを伝えて再提案させる（例:「会議の準備を午前に移して」）
  - 手動でタスクの追加・削除・並べ替えを行う
- AIの役割はあくまで提案であり、最終的な決定は利用者が行う
- タスクはすべて自前のDBで一元管理する

**受け入れ条件:**
- [ ] 利用者の指示をトリガーに、AIが翌日のタスク案を提示できる
- [ ] 既存の未完了タスクから優先順位をつけて提案に含められる
- [ ] Googleカレンダーの予定を参照し、不足するタスクを提案できる
- [ ] 利用者が提案を承認すると、翌日のタスクとして確定される
- [ ] 利用者がフィードバックを伝えると、AIが提案を修正して再提示できる
- [ ] 提案に取り組む順番が含まれ、最初に着手すべきタスクが明確である
- [ ] 利用者が手動でタスクを追加・削除・並べ替えできる

### US-002: 割り込みタスク発生時のタスク再提案

**優先度:** Must

利用者として、割り込みタスクが発生した時にAIにその日のタスクを再提案してもらいたい。なぜなら予定外の作業が入った際に、自分で優先順位を組み直す負荷を減らしたいからだ。

**詳細:**
- 利用者が「割り込みが入った」「予定が変わった」などとAIに伝えると、その日のタスクの再構成を提案する
- AIは以下の情報をもとに再提案を組み立てる
  - 割り込みタスクの内容と緊急度
  - その日の残りのタスク（確定済み）
  - Googleカレンダーの予定（残り時間の把握）
- 再提案の内容には以下を含む
  - 割り込みタスクの挿入位置
  - 押し出されるタスクの扱い（翌日以降への繰り越し、削除など）
- US-001と同様に、利用者は承認・フィードバック・手動操作で最終決定する

**受け入れ条件:**
- [ ] 利用者がAIに割り込みタスクの発生を伝えられる
- [ ] AIが割り込みを踏まえて、その日のタスクを再構成して提案できる
- [ ] 押し出されるタスクについて、繰り越しなどの扱いが提案される
- [ ] 利用者が再提案を承認・フィードバック・手動操作で確定できる

### US-003: AIによる次のタスク提案とステータス進行

**優先度:** Must

利用者として、次に取り組むべきタスクをAIに提案してもらい、承認や完了の操作でステータスを進めたい。なぜなら「次は何をやろう」と迷う時間をなくし、目の前のタスクに集中したいからだ。

**詳細:**
- タスクには以下のステータスがある
  - 未着手 / 着手中 / 完了 / 中止
- 一日の最初のタスクは、US-001で確定した順番に基づいてAIが提案する
- AIがその日のタスクの中から、次に取り組むべきタスクを提案する
- 利用者が承認すると、そのタスクのステータスが「着手中」になる
- 利用者が完了を宣言すると、そのタスクのステータスが「完了」になる
- 完了後、AIが次のタスクを提案する（繰り返し）
- US-001と同様に、提案に対してフィードバックや手動操作も可能

**受け入れ条件:**
- [ ] 一日の最初の提案は、US-001で確定した順番に基づいている
- [ ] AIがその日のタスクから次に取り組むべきタスクを提案できる
- [ ] 利用者が提案を承認すると、タスクのステータスが「着手中」になる
- [ ] 利用者が完了を宣言すると、タスクのステータスが「完了」になる
- [ ] タスク完了後、AIが次のタスクを提案できる
- [ ] 利用者がフィードバックや手動操作で別のタスクを選べる

### US-004: 一日の終わりの未完了タスク振り返り

**優先度:** Must

利用者として、一日の終わりに未完了のタスクについてAIに確認してもらいたい。なぜなら未完了タスクを放置せず、すべてのタスクのステータスを確定した状態で一日を終えたいからだ。

**詳細:**
- 利用者が「寝る」など一日の終わりを告げると、AIがまず未完了タスクの振り返りを開始する
- 各未完了タスクに対して、利用者は以下のいずれかを宣言する
  - 完了した（ステータスを「完了」に変更）
  - 今度やる（ステータスを「未着手」に戻し、繰り越す）
  - 中止（ステータスを「中止」に変更）
- 「今度やる」または「中止」を選んだ場合、AIが未達成の理由を問い、利用者が回答する
  - 記録された理由は、AIがアドバイス・タスク作成・優先順位づけを行う際の参考情報として活用される
- 「今度やる」を選んだ場合、タスクを複製して翌日の日報に紐づける
  - 元のタスクはその日の記録としてそのまま残る
  - 複製されたタスクは繰り越し元への参照を持ち、AIが先延ばしパターンを検出する材料になる
- すべてのタスクのステータスが確定したら、US-005（日報作成）に移行する

**受け入れ条件:**
- [ ] 「寝る」など一日の終わりを告げる発言をトリガーに、AIが未完了タスクの一覧を提示できる
- [ ] 各タスクに対して「完了した」「今度やる」「中止」を宣言できる
- [ ] 「今度やる」「中止」を選んだ場合、AIが未達成の理由を問い、利用者が回答できる
- [ ] 「今度やる」を選んだ場合、タスクが複製され翌日の日報に紐づけられる
- [ ] 複製されたタスクが繰り越し元のタスクへの参照を持つ
- [ ] 宣言に応じてタスクのステータスが正しく更新される
- [ ] すべてのタスクのステータスが確定するまで振り返りが続く
- [ ] 振り返り完了後、US-005（日報作成）に移行する

### US-005: AIによる日報作成支援

**優先度:** Must

利用者として、一日の終わりにAIに日報を書いてもらいたい。なぜなら日報作成の手間を最小限にしつつ、その日の活動を正確に記録したいからだ。

**詳細:**
- US-004（未完了タスクの振り返り）が完了した後、AIが日報の作成を促す
- AIはその日のタスクの結果（完了・繰り越し・中止）をもとに日報の内容を提案する
- 日報はWhat? So What? Now What?（Borton 1970 / Driscoll 1994 / Rolfe et al. 2001）に基づくセクション構成を持つ
  - What?（何が起きたか）はタスクの記録で代替される
  - So What?（何を得たか）: 良かった点 / 良くなかった点 / 学び・気づき
  - Now What?（次にどうするか）: 次にやること
  - その他: 上記に収まらない自由記述
- 日報の内容を埋めるための情報が不足している場合、AIが利用者に質問して補完する
  - 例:「このタスクで苦労した点はありますか？」「会議の結論は何でしたか？」
- 提案に対して、利用者は以下の操作ができる
  - 承認する（提案内容をそのまま日報として確定する）
  - AIにフィードバックを伝えて修正させる
  - 手動で日報の内容を編集する
- 確定した日報はDBに保存される

**受け入れ条件:**
- [ ] US-004完了後、AIが日報の作成を促せる
- [ ] その日のタスク結果をもとに、AIが日報の内容を提案できる
- [ ] 日報がセクション構成（良かった点・良くなかった点・学び気づき・次にやること・その他）を持つ
- [ ] 情報が不足している場合、AIが利用者に質問できる
- [ ] 利用者が提案を承認・フィードバック・手動編集で確定できる
- [ ] 確定した日報がDBに保存される

### US-006: AIによる週報作成支援

**優先度:** Must

利用者として、週の最初に目標を設定し、週の終わりにAIに週報の振り返りを書いてもらいたい。なぜなら一週間の行動に方向性を持たせつつ、振り返りの手間を最小限にしたいからだ。

**詳細:**
- 週報は2段階のライフサイクルを持つ
  - 週の最初: 利用者がその週の目標を記入して週報を作成する
  - 週の終わり: AIが振り返りの内容を提案し、利用者が追記して完結する
- 週の終わりの振り返りでは、AIはその週のタスク結果と日報をもとに週報の内容を提案する
- 提案に対して、利用者は以下の操作ができる
  - AIにフィードバックを伝えて修正させる
  - 手動で週報の内容を編集する
- 利用者が「確定」すると、週報がDBに保存される

**受け入れ条件:**
- [ ] 週の最初に、利用者がその週の目標を記入して週報を作成できる
- [ ] 週の終わりに、AIが振り返りの内容を提案できる
- [ ] その週のタスク結果と日報をもとに、AIが週報の内容を提案できる
- [ ] 利用者がフィードバック・手動編集で内容を修正できる
- [ ] 利用者が確定すると、週報がDBに保存される

### US-007: AIによる月報作成支援

**優先度:** Must

利用者として、毎月固定のタイミングでAIに月報を書いてもらいたい。なぜなら月単位の振り返りを手間なく記録し、長期的な活動の傾向を把握したいからだ。

**詳細:**
- 毎月固定の日（アプリ側で事前に設定）に、AIが月報の作成を提案する
- 利用者が作成すると答えると、月報作成画面が表示される
- AIはその月のタスク結果・日報・週報をもとに月報の内容を提案する
- 提案に対して、利用者は以下の操作ができる
  - AIにフィードバックを伝えて修正させる
  - 手動で月報の内容を編集する
- 利用者が「確定」すると、月報がDBに保存される

**受け入れ条件:**
- [ ] アプリ側で設定された固定の日に、AIが月報の作成を提案できる
- [ ] その月のタスク結果・日報・週報をもとに、AIが月報の内容を提案できる
- [ ] 利用者がフィードバック・手動編集で内容を修正できる
- [ ] 利用者が確定すると、月報がDBに保存される

### US-008: AIによるプロジェクト作成支援

**優先度:** Must

利用者として、AIとの対話を通じて新しいプロジェクトを作成したい。なぜならプロジェクトの内容を一から整理する手間を減らし、必要な情報が揃った状態でプロジェクトを始めたいからだ。

**詳細:**
- 利用者が「新規プロジェクトを作りたい」などと指示すると、AIがプロジェクト作成を開始する
- AIがプロジェクトに必要な情報を埋めるために質問する
  - 例: プロジェクト名、目的、期限など
- 利用者の回答をもとに、AIがプロジェクトの内容を提案する
- 提案に対して、利用者は以下の操作ができる
  - AIにフィードバックを伝えて修正させる
  - 手動でプロジェクトの内容を編集する
- 利用者が確定すると、プロジェクトがDBに保存される
- タスクはプロジェクトに紐づけられる（プロジェクト → タスクのフラットな構造）
- プロジェクトに属さないタスクもあり得る（例: 日常的な雑務）

**受け入れ条件:**
- [ ] 利用者の指示をトリガーに、AIがプロジェクト作成のための質問を開始できる
- [ ] AIが利用者の回答をもとにプロジェクトの内容を提案できる
- [ ] 利用者がフィードバック・手動編集で内容を修正できる
- [ ] 利用者が確定すると、プロジェクトがDBに保存される
- [ ] タスクをプロジェクトに紐づけられる
- [ ] プロジェクトに属さないタスクも作成できる

### US-009: レポート・タスク履歴の閲覧

**優先度:** Must

利用者として、過去の日報・週報・月報とタスクの履歴を一覧・詳細で閲覧したい。なぜなら過去の活動を振り返り、自分の行動傾向や進捗を把握したいからだ。

**詳細:**
- 利用者がレポートの一覧画面にアクセスすると、日報・週報・月報それぞれの一覧を閲覧できる
- 一覧から特定のレポートを選択し、詳細を閲覧できる
- レポートの詳細から、その期間のタスクも閲覧できる
- 表示形式（リスト、カレンダーなど）はUI設計時に決定する

**受け入れ条件:**
- [ ] 利用者がレポートの一覧画面にアクセスできる
- [ ] 日報・週報・月報それぞれの一覧を閲覧できる
- [ ] 一覧から特定のレポートを選択し、詳細を閲覧できる
- [ ] レポートの詳細から、その期間のタスクを閲覧できる

### US-010: ダッシュボード

**優先度:** Must

利用者として、アプリを開いた時に今の状況を一目で把握したい。なぜなら現在の状態を確認するために複数の画面を行き来したくないからだ。

**詳細:**
- アプリを開くと、ダッシュボードが表示される
- ダッシュボードには以下の情報が集約される
  - 今日のタスク一覧（ステータスつき）
  - 明日のタスク一覧（確定済みの場合）
  - プロジェクト一覧
- 各項目から詳細画面へ遷移できる

**受け入れ条件:**
- [ ] アプリを開くとダッシュボードが表示される
- [ ] 今日のタスク一覧がステータスつきで表示される
- [ ] 明日のタスク一覧が表示される（確定済みの場合）
- [ ] プロジェクト一覧が表示される
- [ ] 各項目から詳細画面へ遷移できる
