# 非機能要件

本ドキュメントでは、システムが「どのように動くべきか」を定義する。
品質特性の分類は ISO/IEC 25010:2011（SQuaRE）に基づく。

## ISO 25010 とは

ソフトウェア製品の品質を評価するための国際標準規格である。
品質を8つの特性に分類し、各特性をさらに副特性に細分化する。
すべての副特性を網羅する必要はなく、プロジェクトに関係するものだけを定義すればよい。

## 凡例

各要件には以下の優先度を付与する。

| ラベル | 意味 |
|---|---|
| Must | 初回リリースに必須 |
| Should | 早期に対応したいが、初回リリースには必須ではない |
| Could | あると望ましいが、なくても成立する |
| Won't | 今は対応しない。将来の検討事項 |

---

## 1. 機能適合性（Functional Suitability）

機能がユーザーの目的やニーズをどの程度満たすかに関する特性。

> 機能要件はユーザーストーリー（user-stories.md）で定義済みのため、ここでは補足的な観点のみ記載する。

### 1.1 対象プラットフォーム

**優先度:** Must

- Web アプリケーションとして提供する

**優先度:** Won't

- 将来的に Mac 向けの GUI もしくは TUI を検討する

### 1.2 対象ユーザー

**優先度:** Must

- 自分専用の個人利用アプリとする
- マルチユーザー対応は行わない

### 1.3 外部連携

**優先度:** Must

- Google カレンダーとタスクを紐づける（US-001, US-002 で参照）
- GitHub のコントリビューション情報を取得し、AI が日報の内容を提案する際の材料にする

### 1.4 AIエージェントによる操作

**優先度:** Must

- [OpenClaw](https://openclaw.ai/)（AIエージェント）がこのアプリを操作することを前提とした設計にする
- OpenClaw はチャットアプリ（Telegram, Discord 等）経由でシステムを操作する AI エージェントである
- これにより、利用者は Web UI を直接操作するだけでなく、チャットを通じて AI にアプリ操作を委任できる
- 設計上の要件:
  - バックエンドは API ファーストで設計し、すべての操作を API 経由で実行可能にする
  - API は OpenClaw が解釈・操作しやすいよう、RESTful かつ一貫した設計にする
  - Web UI は API のクライアントの1つという位置づけにする

## 2. 性能効率性（Performance Efficiency）

システムの応答速度やリソース使用量に関する特性。

### 2.1 応答時間

操作の性質によって2つの基準を設ける。

#### 通常操作（画面遷移、タスク作成、ステータス変更など）

**優先度:** Must

- API 応答は **1秒以内** とする（Nielsen の「思考の流れが途切れない」閾値）

#### AI操作（タスク提案、日報生成など）

**優先度:** Must

- **10秒以内** に応答を開始する（Nielsen の「注意を維持できる限界」閾値）
- 体感待ち時間を軽減するため、ストリーミング表示などの工夫を行う

#### Web UI の描画性能（Core Web Vitals）

**優先度:** Should

| 指標 | 基準値 | 説明 |
|---|---|---|
| LCP（Largest Contentful Paint） | < 2.5秒 | 最大コンテンツが描画されるまでの時間 |
| INP（Interaction to Next Paint） | < 200ms | ユーザー操作から次の描画までの時間 |
| CLS（Cumulative Layout Shift） | < 0.1 | レイアウトのずれの累積量 |

### 2.2 同時利用者数

**優先度:** Must

- 1人（個人利用）

## 3. 互換性（Compatibility）

他のシステムや環境との共存・連携に関する特性。

### 3.1 対応ブラウザ・デバイス

**優先度:** Must

- 主要ブラウザ（Chrome, Firefox, Safari, Edge）の最新版で動作すること
- PC での利用を前提とする

**優先度:** Won't

- 将来的にスマートフォンでの利用を検討する

### 3.2 外部サービスとの相互運用

**優先度:** Must

- Google カレンダー API と連携する
- GitHub API と連携する（コントリビューション情報の取得）
- AI API と連携する（提案・分析機能の実現）

---

## 4. ユーザビリティ（Usability）

利用者にとっての使いやすさに関する特性。

### 4.1 操作性

**優先度:** Must

- 直感的に操作できる UI を目指す
- 初見でも迷わず主要な操作（タスク管理、レポート閲覧）ができること

### 4.2 アクセシビリティ

- 身体的な制約がないため、特別なアクセシビリティ対応は行わない

---

## 5. 信頼性（Reliability）

システムが正常に動作し続けることに関する特性。

### 5.1 可用性

**優先度:** Should

- 個人利用のため厳密な SLA は不要だが、日常的に安定して使えること
- 障害発生時は速やかに復旧できる構成にする

### 5.2 データ永続性

**優先度:** Must

- データの消失は許容しない
- 定期的な自動バックアップを行い、障害時にデータを復元できること
- バックアップの具体的な方式（頻度、保存先、世代管理）は設計フェーズで決定する

---

## 6. セキュリティ（Security）

データ保護やアクセス制御に関する特性。

### 6.1 ネットワークセキュリティ

**優先度:** Must

- Tailscale 経由でのみアクセスする（パブリックインターネットに公開しない）

### 6.2 認証方式

**優先度:** Must

- API Key（静的トークン）による認証を採用する
- すべての API リクエストに `Authorization: Bearer <key>` ヘッダを要求する
- Key は環境変数で管理し、ソースコードに含めない
- 定期的なローテーションは行わず、漏洩が疑われた時に手動でリセットできる仕組みを用意する

### 6.3 多層防御

**優先度:** Must

- スイスチーズモデル（James Reason）に基づき、不必要な穴を作らない
- 防御層の構成:
  - 第1層: Tailscale によるネットワークレベルの保護
  - 第2層: API Key によるアプリケーションレベルの認証
  - 第3層: 入力値バリデーションによるデータレベルの保護
- 既知の脆弱性に対する緩和策:
  - API Key は Web UI では HttpOnly Cookie に保存する（XSS による窃取を防ぐ）
  - ログ出力時に Authorization ヘッダをマスクする（ログ経由の漏洩を防ぐ）
  - API Key の比較は定数時間比較で行う（タイミング攻撃を防ぐ）
  - 認証失敗をログに記録する（不正アクセスの試行を検知する）
- 外部 API キー（Google, GitHub, AI）は環境変数等で管理し、ソースコードに含めない

## 7. 保守性（Maintainability）

システムの修正・拡張のしやすさに関する特性。

### 7.1 テスト戦略

**優先度:** Must

- テストは以下の3層で構成する

| 層 | 対象 | 目的 | 方針 |
|---|---|---|---|
| ユニットテスト | ビジネスロジック、純粋関数 | 個々の関数が正しく動作することを保証する | 積極的に書く |
| インテグレーションテスト | API エンドポイント | リクエストからレスポンスまでの一連の流れを保証する | 主要な正常系・異常系を書く |
| E2E テスト | 画面操作 | ユーザーの操作フローが動作することを保証する | クリティカルパスのみ書く |

- テストフレームワークやカバレッジ目標は技術選定時に決定する

### 7.2 コード品質

**優先度:** Must

- リンターを導入し、コードの一貫性を保つ
- フォーマッターを導入し、スタイルの議論を排除する
- 型のある言語・フレームワークを採用し、型安全性を確保する
- 具体的なツールは技術選定時に決定する

### 7.3 CI（継続的インテグレーション）

**優先度:** Should

- コードの push 時に以下を自動実行する
  - リンター
  - フォーマッターのチェック
  - テストの実行
- CI 環境は GitHub Actions を使用する

### 7.4 ログ方針

**優先度:** Should

- 構造化ログ（JSON 形式等）を採用し、機械的に解析可能にする
- ログレベルを使い分ける

| レベル | 用途 |
|---|---|
| ERROR | 復旧が必要な異常 |
| WARN | 異常だが処理は継続できる |
| INFO | 正常な操作の記録（API リクエスト、認証成功等） |
| DEBUG | 開発時のデバッグ情報。本番では出力しない |

---

## 8. 移植性（Portability）

異なる環境への移行・適応のしやすさに関する特性。

### 8.1 デプロイ環境

**優先度:** Must

- Proxmox 上の LXC コンテナ（Ubuntu 24.04）にデプロイする
- Tailscale 経由でアクセスする（6.1 ネットワークセキュリティ参照）

### 8.2 環境依存性

**優先度:** Must

- LXC 上で動作するものを前提とし、特定の OS ディストリビューションへの依存を最小限にする
